> 分析对象：Parlant 源码 v3.3.1 + 官方可观测性文档。本文说明 Parlant 的可追溯数据从哪来、长什么样，以及如何接入 langfuse 等追踪系统。

# 可观测性与追踪对接（OpenTelemetry / langfuse）

---

## 一、Parlant 原生可观测性

Parlant **内置 OpenTelemetry（OTL）支持**，无需改代码即可导出 traces / metrics / logs 到任意 OTLP 兼容后端（Jaeger、Grafana、Datadog、**langfuse** 等）。

启用方式（环境变量）：

| 变量 | 作用 |
|---|---|
| `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` | 启用 tracing 并指定 OTLP 端点 |
| `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` | 启用 metrics 并指定端点 |
| `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` | 启用 logs 并指定端点 |

常用可选配置：`OTEL_EXPORTER_OTLP_PROTOCOL`（grpc/http/protobuf，默认 grpc）、`OTEL_SERVICE_NAME`（默认 `parlant`）等。

> 未配置端点时的回退：tracing 用内存 tracer、metrics 用本地记录 meter、logs 写到 `parlant-data/parlant.log`。本地开发零依赖。

---

## 二、可观测数据的两个层面

### 1. 会话事件流（业务层，前端可直接消费）

每个会话事件（`EmittedEvent`，见 `core/emissions.py`）都带 **`trace_id`**：

```python
EmittedEvent(source, kind, trace_id, data, metadata)
#            谁发的   类型   贯穿ID   载荷   元数据
```

- `kind`：`STATUS`(acknowledged/processing/ready/error/cancelled) / `MESSAGE` / `TOOL` / `CUSTOM`
- `trace_id`：与该次响应产生的 OpenTelemetry trace 一一对应。

**关联方法**（对应官方文档"Correlating Traces with Sessions"）：
1. 前端发现一条有问题的回复；
2. 取该事件的 `trace_id`；
3. 在追踪后端按 `trace_id` 检索；
4. 还原完整处理流水线。

### 2. OpenTelemetry Span（引擎内部执行层）

引擎自动埋点的关键 span（对应 `tracer.py` 与官方文档）：

| Span 名称 | 含义 |
|---|---|
| `process` | 处理事件的主循环（一次提问的主 span） |
| `utter` | 智能体话术生成入口 |
| `message_generation` | 消息组合流水线（Prompt 组装 + LLM 生成） |
| `guideline_matcher` | 指南匹配（属性 `phase` = `initial` / `reevaluation`） |
| `tool_caller` | 工具执行 |
| `response_analysis` | 回复质量分析 |
| 更细粒度 | LLM 调用、embedder 调用等 |

关键指标（metrics）：`message_generation_duration`、`ttfm_duration`（首消息耗时）、`match_duration`（指南匹配耗时）等。

## 三、接入 langfuse 的方案

langfuse 原生支持 OTLP 接入，因此让 Parlant 的追踪进入 langfuse 只需把 OTLP 端点指向 langfuse。

### 方案 A：langfuse 自托管 / Cloud 的 OTLP 端点

```bash
# 指向 langfuse 的 OTLP collector（具体 host:port 以你的 langfuse 部署为准）
export OTEL_EXPORTER_OTLP_TRACES_ENDPOINT="http://<langfuse-host>:4318/v1/traces"
export OTEL_EXPORTER_OTLP_PROTOCOL="http/protobuf"
export OTEL_SERVICE_NAME="parlant-agent-server"
```

启动 Parlant 服务后，每个 span 都会作为 trace/observation 出现在 langfuse，可用 `trace_id` 与会话事件互查。

### 方案 B：通过 OTel Collector 中转（推荐生产用）

Parlant → OTel Collector → langfuse（同时可分发到 Prometheus/Grafana）。Collector 配置接收 OTLP、导出到 langfuse 的 ingestion endpoint。

### 方案 C：二次开发时埋点（扩展 `configure_api` / hooks）

在自建后端（`parlant-agent-server`）里：
- 用 `configure_api` 加请求级中间件，记录 API 层 trace；
- 用引擎 `Hooks`（`on_generating_messages`、`call_on_preparation_iteration_start` 等）在关键阶段写自定义 span/annotation；
- 把 `agent_id` / `session_id` / `customer_id` 作为 span attribute，便于在 langfuse 按维度过滤。

## 四、对你三个项目的落地建议

| 项目 | 追踪要点 |
|---|---|
| `parlant-agent-web`（聊天窗口） | 显示每条消息事件的 `trace_id`，点击可跳到 langfuse 查看该次回复的完整 span 树 |
| `parlant-agent-server`（调度服务） | 统一注入 `OTEL_*` 环境变量；按 `agent_id`/`session_id` 打 attribute；用 `configure_api` 加 API 层 span |
| `parlant-agent-admin`（配置前端） | 配置页可展示某 agent 的历史 trace 聚合（匹配耗时、工具调用分布、指南命中率） |

---

## 五、小结

- **可追溯的根**：`EmittedEvent.trace_id` 贯穿"会话事件 ↔ OTel trace"两侧。
- **接入成本**：纯配置（环境变量）即可进 langfuse，零代码。
- **可控性的延伸**：langfuse 里能看到每次回复命中的指南匹配、工具调用、消息生成耗时，正是"可控、可追溯"目标的直观呈现。
