## 〇、开场（2 分钟）：一句话定位 + 钩子

**[讲稿]** "今天我们聊的是：如何让 AI 客服**既能像真人一样灵活，又像制度一样可控**。多数方案的痛点是——要么死板（写死的流程树），要么失控（纯提示词，乱承诺）。我们这套方案用一套叫 **Parlant** 的框架，把「行为规则」和「模型能力」分开管理，下面我用 30 分钟讲清楚它为什么不一样，并用一个**智能投顾 Demo** 现场演示。"

钩子（选一）：
- 合规向客户："金融场景最怕 AI 乱承诺。Parlant 的护栏是**结构性的**——客户没做风险测评时，系统在机制上就无法说'你可以买'，不是靠提示词碰运气。"
- 提效向客户："改客服话术/流程，要不要发版？我们这里**改一条指南、保存、立即生效**，业务同事也能上手。"

## 一、行业痛点与「Context Engineering」新思路（8 分钟）

**痛点三连**（每张一页）：
1. 纯 Prompt：上下文塞满 → 模型"听不进去"→ 幻觉、乱承诺
2. 写死流程树：只能走预设分支 → 客户绕两句就卡死（官方原话：传统聊天机器人的僵硬来自**强制分支的流程树**，不是措辞）
3. 改需求=改代码：上线慢，业务无法参与

**Parlant 的回答 = Context Engineering（上下文工程）**：
> 官网定义：把「正确的上下文——不多不少——在正确的时机注入提示词」。正确的不进来会**幻觉**（无依据），错误的不进来会"对着墙说话"（模型被无关内容干扰）。

**[讲稿]** "Prompt Engineering 解决'模型拿到对的上文时如何表现'，Context Engineering 解决'**该放什么进去、什么时候放**'。前者管'怎么回答'，后者管'回答什么'。两者互补，但只调 prompt 不解决上下文污染。"

配套图建议：三层漏斗图（全部规则/知识/工具 → 引擎每轮动态筛选 → 只注入本轮相关的几条）。

## 二、Parlant vs LangGraph：关联与对比（7 分钟，重点）

**一句话定位（官方原文转述，建议直接引用）**：
> "LangChain / LangGraph 是**工作流工具**——管理数据如何在步骤间流动；Parlant 在**更高一层抽象**工作——它管理**行为**。不画节点和边，而是定义行为规则（指南）与它们之间的关系，由框架决定每轮哪些规则生效。"

**对比表（PPT 一页）**：

| 维度 | LangGraph | Parlant |
|---|---|---|
| 抽象层次 | 图执行引擎（节点/边/状态机） | 行为编排层（指南/旅程/关系） |
| 谁来定义 | 开发写代码 | 业务规则 + 少量工程配置，**内容化** |
| 改行为成本 | 改图结构 → 改代码 → 发版 | **加一条指南 = 内容变更，即时生效** |
| 护栏 | 靠测试/人工 | **结构化、确定性**（缺字段自动否决候选回复） |
| 复杂度风险 | 图越画越大，第 200 个节点很危险 | **官方：第 200 条指南和第 1 条一样安全** |
| 灵活性 | 由你写 | 保留 LLM 自然对话，特殊场景才需规则 |

**关系不是对立，是互补**：
- 简单说：**LangGraph 管"流程怎么跑"，Parlant 管"会话怎么说"**。
- 落地组合建议：Parlant 做会话行为层（指南/旅程/话术/护栏）→ 通过**工具调用**接到 LangGraph/已有工作流（订单、审批、计费）→ 再到底层业务系统。
- 我们平台已经按这个思路做了：`journey 节点 → 工具 → 外部业务系统`（Demo 里的 `get_customer_profile`/`transfer_to_human` 就是例子）。

## 三、框架核心可发挥的场景（5 分钟，替客户"对号入座"）

| 场景 | 为什么 Parlant 合适 |
|---|---|
| **强合规/强监管**（金融、保险、医疗） | 结构性护栏：没测评就不能推荐；话术可锁定（strict 话术）；行为可审计 |
| **高频售前/售后客服** | 话术/流程快速迭代、业务同事可调、7×24、多轮不跑偏 |
| **长流程/多步骤**（投顾、理财、合同、报修） | 旅程分叉 + 工具调用 + 变量追踪客户状态，跨节点保持上下文 |
| **"个性化但可控"** | 同一 Agent 按客户画像/变量走不同分支（Demo：已测评 vs 未测评） |
| **需可观测可复盘** | 每轮链路可追溯（langfuse）、命中哪条指南/旅程清晰可见 |
| **不想被单一模型绑架** | LLM 无关，OpenAI/Anthropic/Emcie 任意切换 |

## 五、Demo：智能投顾 Agent 问答（15 分钟，重头戏）

> 环境：AgentStudio 模拟对话页；客户数据来自真实业务系统（invest-advisor-demo，模拟券商后台）。

**[开场定调]** "这是一个对接了真实业务系统的智能投顾——查画像、查行情、做风评、转人工，都真实调后端接口。"

**流程 ① —— 客户画像驱动分支（核心亮点，必演）**
- 选客户 `cus_002 李女士`（VIP、已完成风评、等级 C4）：
  - 问："你好，我想了解下适合我的理财产品"
  - 期望：引擎自动拉画像 → **跳过风险评估** → 直接展示 C4 风险等级 + 匹配产品
- 切客户 `cus_001 张先生`（未做风评）：
  - 同样问 → 期望：**进入风险评估流程**，先做测评再推荐
  - **[讲稿]** "同一个 Agent，两个客户两种走向——不是写死的 if-else，是引擎根据客户变量实时决定。"

**流程 ② —— 工具调用（演示"会干活"）**
- "现在黄金多少钱？" → 期望：调行情工具 → 返回实时价（如 2385.4 美元/盎司）

**流程 ③ —— 犹豫挽留 + 转人工（演示"灵活且可控"）**
- "我再考虑考虑 / 我不想买了" → 期望：命中犹豫节点 → 挽留话术
- "我要找人工顾问" → 期望：**强制转人工**（调 `transfer_to_human` 返回工单号/客服代码）→ 落到坐席
  - **[讲稿]** 转人工是兜底规则（优先级与旅程持平，机制上不会被旅程"压掉"）——这就是"结构性护栏"的现场证据。

**演示配套动作（有时间才做）：**
- 现场改一条话术 → 保存草稿 → 试跑生效（**"改内容不改结构"**的实锤）
- 点某一轮回复的"查看链路" → 展示 langfuse 完整执行树

**⚠️ 防翻车清单（必读）**：
- **演示前 10 分钟**预热一次会话（冷启动 embedding 缓存慢，首次可能卡顿）
- 免费模型配额会耗尽、上游偶发空响应 → 提前确认模型可用，**关键分支先自测一遍**；准备录屏兜底
- LLM 有随机性 → 用"引导话术"（如上）触发期望分支，别裸考
- 转人工分支依赖 `gdl_force_transfer` 已发布生效（当前仍是示例草稿，演示前须在线上定义发布）

## 七、结尾 CTA + Q&A 准备（3 分钟）

- **CTA（三选一）**：① 用你们的业务场景做一次 POC（最快 1~2 周出 Demo）② 安排一次技术深聊 ③ 提供定制 Demo（用你们的客户/产品数据）。
- **Q&A 弹药**：
  - "贵司数据安全？" → 本地化部署（Mongo/MySQL/引擎全自托管）、langfuse 可自建。
  - "换模型影响大吗？" → LLM 无关；行为规则与模型解耦，切换成本低。
  - "能接现有系统吗？" → 任意 HTTP 工具即可对接订单/CRM/工单系统（Demo 即是）。
  - "业务人员能自己改吗？" → 指南/旅程/话术均在界面配置，无需发版。
  - "效果怎么保证？" → 结构化护栏 + 自动仿真回归 + 每轮链路可审计。
