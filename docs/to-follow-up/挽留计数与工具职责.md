# 挽留计数与 tool→fork 分支（journey_node_counter 差 1 → 走通实录）

> **状态：已解决**（2026-09-28 更新）。
> - **tool→fork 已走通**：真正根因是 **loader 缺 REEVALUATION 关系**（不是引擎不支持、不是"版本不匹配"）。
> - **差 1 问题**在 fork 结构下语义自洽（counter 按"拒绝次数"计，与挽留分支一一对应）。
> - 本文是完整排查实录 + 工具职责分析 + 通用设计结论 + 插桩变更记录，供后续复用与维护。
> 触发场景：提前结清旅程（`onb-094c4bbe2663`）挽留环节——客户拒绝次数计数与实际挽留动作对不上 + tool 后分支跑不通。

## 二、根因（按排查时间序）

### 2.1 差 1 现象（session_messages 实证）

两条草稿会话，`journey.progress` 路径与台账（`session_messages`）实际消息对不上：

| 会话 | 工具调用日志（journey_node_counter） | 实际挽留话术（session_messages） |
|---|---|---|
| `0Gm2crnVdQ` | 1 次（count=1） | 2 次（msg6 @node9 + msg9 @node10） |
| `tVaRkvMLfq` | 2 次（count=1→2） | 3 次（msg7 @node9 + msg10 @node10 + msg12 @node9回环） |

**工具调用次数 = 挽留次数 − 1，两条恒成立。**

> **教训**：判断"挽留了几次 / 计数对不对"，**必须以 `session_messages` 实际消息为准**。
> `journey.progress` 路径只反映节点转移，不反映 agent 在某节点内说了几句挽留。
> （本次排查初期就因只看路径、误判"计数正常"，被用户两次纠正。）

### 2.2 差 1 的三层机制（引擎时序 + 计数粒度 + 判断非确定）

**① 引擎执行时序**（一条客户消息 = 一步完成）：
1. 对当前节点做出边选择 → 2. 推进到下一节点 → 3. 执行新节点动作（chat=生成话术 / tool=调工具）→ 4. agent 回复。
- **当前节点的出边选择**发生在**下一条客户消息**；**推进**与**新节点动作**在**同一轮**。

**② 计数粒度 ≠ 挽留粒度（差 1 的真正来源）**：
- `journey_node_counter` 按 **node 10 入口**计数（每次 `9→10` 转移 +1）；
- 挽留动作既发生在 node 9（回环后重新进入），也发生在 **node 10 内部**：工具返回 `count=1`（未达上限）后，agent 在**同一轮响应里继续劝说**——这次挽留**不触发工具**（无新转移）；
- → 挽留次数恒比工具计数多 1。

**③ 条件选择 LLM 手里有两个矛盾信号**：
node 10 出边条件（`次数<2` / `≥2`）由 LLM 判断，但 LLM 看到：
- 工具结果 `count=1`（漏计的）；
- transcript 里数出的拒绝次数 = 2（客户确实拒了两次）。
两个信号对不上，两条会话各信一个（一个信 transcript 直接跳预约、一个信工具回环多挽留一轮）。

**④ 工具调用是 LLM 决定（非确定）——"进入 tool 节点 ≠ 调用工具"**：
`journey_node_counter` 本体（`builtin_tools.py:49-74`）只是内存 dict 按 `(agent_id, session_id)` +1 返回 `{"count": N}`——**它连自己在哪个节点都不知道**（`ToolContext` 只暴露 agent_id/session_id/customer_id，**不暴露节点 id**，docstring 自认局限）。它数的是"本会话被调了几次"，不是"某节点被访问了几次"。

触发时机：挂在 tool 节点 → 节点指南命中 → 进 `tool_enabled_guideline_matches` → 引擎 `infer_tool_calls()`（`tool_caller.py:174`）→ `batch.process()`——**这是一次生成式推理，LLM 当场决定调不调、传什么参数** → 调了才执行（`engine.py:705`）。

> **进入 tool 节点 ≠ 一定调工具。** `1adtJC4UEJ` 0 次调用、`tVaRkvMLfq` 调 2 次——同样的节点，LLM 每次决定不一样。

### 2.3 tool→fork 不推进的真正根因：loader 缺 REEVALUATION 关系 ★（本次核心修复）

**现象**：tool 节点（counter）后接 fork 按次数路由，但 tool 节点滞留——迭代2 就地吐一句（路径停在 `[...9,10]`），下一条客户消息才路由。

**源码追踪**（v3.3.1）：
1. 引擎主循环 `while not prepared_to_respond`（`engine.py:343`）；迭代1 工具执行后 `executed_tools` 非空 → `_check_if_prepared` 返回 False（`engine.py:600`）→ 进迭代2。
2. 迭代2 `_run_additional_preparation_iteration` → `find_guidelines_that_need_reevaluation`（`entity_cq.py:390`）靠 **「journey_node_tag → tool」的 REEVALUATION 关系**反查旅程 → 投影出节点指南 → 重建旅程批处理 → next-step 推进 tool 出边。
3. **而 REEVALUATION 关系只在 SDK 的 `_transition()`（fluent API，`sdk.py:1520`）里创建**；我们的 `agent_loader.py` 直接 `journey._create_state` + `create_transition`，**绕过了 `_transition`** → 关系没建 → 重评估返回 0 条（实测 `engine.reeval ... reevaluate=0 journey_nodes=0`）→ 旅程批处理不跑 → tool 出边不推进 → 滞留。

**修复**（`agent_loader.py _build_journey`）：建 tool 状态时按 SDK 同款补建 REEVALUATION 关系：
```python
if tools:
    relationship_store = self._server.container[RelationshipStore]
    for t in tools:
        await relationship_store.create_relationship(
            source=RelationshipEntity(id=_Tag.for_journey_node_id(state.id).id, kind=RelationshipEntityKind.TAG_ALL),
            target=RelationshipEntity(id=_tool_ref_to_id(t), kind=RelationshipEntityKind.TOOL),
            kind=RelationshipKind.REEVALUATION,
        )
```
`create_relationship` 是 **upsert**（`update_one upsert=True`），reload 幂等。

**修复后验证**（两次拒绝，全在单轮迭代2完成）：
| 客户消息 | counter | fork 路由 | 结果 |
|---|---|---|---|
| 确定需要提前还款（1次） | count=1 | <2次→node9 | 挽留话术2 ✓ |
| 确定需要提前还款（2次） | count=2 | ≥2次→node13 | 预约引导 ✓ |

实测日志：`engine.reeval ... reevaluate=32` → `batch_enter last=10` → `auto_return 放弃快路径：fork 12 有 2 个分支，转 next-step` → `next_step current=10 命中条件[2] -> path=['12','9']` → `journey.progress iter=2 paths=[...,'9','10','12','9']`。

> **结论：v3.3.1 引擎原生支持 tool→fork（含多分支）。此前"tool 后分支跑不通"是 loader bug，不是引擎限制。**
> **任何"分支依赖工具结果"的场景都依赖这条 REEVALUATION 关系**——loader 必须补建，是通用修复，不只对 counter。

### 2.4 工具节点一轮 = 工具调用 + 同轮 LLM 回复（机制侧，供理解）

修好关系后 tool 节点干净推进；但理解这条机制仍有价值（tool→chat 单出边场景）：
- **迭代1**：tool 节点指南命中 → 调工具 → `executed_tools` 非空 → 不回复，进迭代2；
- **迭代2**：`message_generation`（`engine.py:397/459`）生成一条用户可见回复——**与工具调用在同一条客户消息内**。
- 迭代2 推进与否取决于是否重建旅程批处理（§2.3）→ 取决于 REEVALUATION 关系。

## 三、设计结论

### 3.1 工具该不该用于"数节点访问次数"

1. **取数**（查询/检索外部）：`tavily_search` / `get_upcoming_slots` / `get_lab_results`；
2. **写状态/副作用**：`variable_update`（写 ContextVariableStore）/ `schedule_appointment`；
3. **结果驱动分支决策**：工具结果写 context variables → 出边条件选择读它（docs/03-production/09）；
4. **支撑结果生成**：检索结果 → 组织成回答。

"数节点访问次数"用于**固定、线性、小上限**的流程属于不必要的过载——Parlant 状态机结构本身就能编码计数（节点身份 + 出边）。counter 工具真正值钱的场景：**上限动态可配（max_value 参数化）、跨多异构节点累计、计数要成为一等业务值被外部读取**。

三层错位（与 §2.2 一一对应）：
| 错位 | 说明 |
|---|---|
| **调用非确定** | 调不调工具是 LLM 决定（§2.2④），不是引擎保证 → 计数可能直接缺失（`1adtJC4UEJ` 0 次） |
| **粒度错位** | 计数时机=「进 node 10 且恰好被调用」，挽留还发生在 node 9 / node 10 内部（§2.2②）→ 恒少 |
| **判断非确定** | 就算 count 对，出边条件仍由 LLM 读两个矛盾信号（count vs transcript）判断（§2.2③） |

### 3.2 三个候选方案（结论更新）

| 方案 | 做法 | 改结构？ | 评价 |
|---|---|---|---|
| A 内容级 | node 10 指令改"只计数、不挽留" | 否 | 改动最小，但靠 LLM 遵从指令，残余风险 |
| B 结构级 | 计数器挪 node 9，node 9 自环直到拒绝≥2 | 是 | 计数=挽留轮次，但引入自环，仍要"读数字"判断 |
| **fork 方案（本次走通）** | `node9(chat) → node10(counter,单出边) → fork(<2→9, ≥2→12)` | 是 | **分支依赖工具结果的标准形态**；count=拒绝次数、路由正确；残余：counter 调用非确定（LLM 可能不调） |
| **C 双节点（最彻底）** | 拆两个挽留节点 9a/9b：9a 拒绝→9b、9b 拒绝→12 | 是 | 结构即计数，无差 1、无条件读数字、无 counter 非确定，观察性好；**不适用"分支必须依赖工具结果"场景** |

> **两者定位不同**：**fork 方案** = "分支依赖工具结果"场景的正解（引擎原生支持，§2.3 已走通）；
> **方案 C** = "固定小上限线性流程"里更彻底的替代（连工具和 fork 都省掉）。
> 本工程保留 fork 方案作为通用能力，挽留环节是否切方案 C 属业务决策（见 §五）。

#### 自环机制（方案 B 的引擎侧解释，保留备查）

自环 = source==target 的转移：`create_transition("客户拒绝且未达挽留上限", node9, node9)`（`sdk.py:2647` 不校验源=目标）。
引擎"重进同一节点"：旅程"当前节点" = `journey_path` 最后一个元素；选自环 → `journey_path.append(9)` → **重新进入 node 9 → 节点动作重执行**。每条"拒绝"= 一次自环 = 一次挽留重执行。推进一次只发生在一条客户消息里，不可能死循环。实证：`tVaRkvMLfq` `msg12 @node9回环`（10→9 重进 node 9 重跑挽留）。

### 3.3 通用设计原则（修正版）：tool 节点后挂 fork 路由

> **本节是本次最重要的认知修正**：早先以为"tool 节点后不能多出边/不能接多分支 fork"（受 bundled docs "must be followed by a chat state" 影响），**实为 loader 缺 REEVALUATION 关系所致**（§2.3）。代码视角：
> - **快路径 `auto_return_match`**（`journey_node_selection_batch.py:173`）：tool+单出边+工具已调 → 自动推进；能穿透**单分支** fork；**多分支 fork 时放弃**（`len(follow_ups)!=1 → return None`）。
> - **兜底路径**（`process()` elif 分支，`:303`）：放弃后对 tool 节点跑 `JourneyNextStepSelection`，prompt 明确"tool 已执行，按工具结果判断下一转移"（`journey_next_step_selection.py:601`）；推进穿透 fork 到目标 chat（`:342-367`）。**该路径依赖 §2.3 的 REEVALUATION 关系**。
> - 结论：**tool → fork（多分支）在 v3.3.1 是引擎原生支持的合法形态**，官方在线文档 "Fork states are most useful when you need to branch after a tool state" 描述准确；bundled `journeys.md`（v3.3.1 附带的文档）滞后于代码。

**tool 节点的干净形态**（fork 方案）：
```
[chat] → [tool 单出边] → [fork 按工具结果路由] → [chat] / [chat]
```

### 3.4 变量泄漏幻觉：`reason` 默认值全量注入 LLM 上下文 ★（新增）

**现象**：草稿会话 `1KSa7larLM` 在预约节点回复里出现"该合同目前存在逾期未还款，需先完成还款后才能办理提前结清"——但该会话走的是 **isEligible=true** 路径（合同可结清、已进挽留/预约），"逾期"信息是幻觉。

**根因链**：
1. `reason` 变量默认值 = `'当前合同存在逾期为还款，请进行还款后才能办理'`（描述："当变量 isEligible 为 false 时，此变量才生效，代表合同不满足办理条件的原因"）——本应只在 isEligible=false 分支（`sta_Lj5AhD` 动作"原因从变量reason中取值"）用。
2. 但引擎 `_load_context_variables` 把**所有变量**按优先级解析后**无差别注入** LLM 上下文（`context_variables_to_json`，`engine.py:1926`），**没有节点级/条件级过滤**。
3. 描述里"仅当 isEligible=false 才生效"只是**文字说明，引擎与 LLM 均不强制**——LLM 在 isEligible=true 的预约节点照样引用了 `reason` 的默认值当"事实提醒"。

**通用教训**：
- **变量默认值不要承载具体业务状态断言**（"该合同存在逾期…"这种"当前对象"断言），因为默认值**全局注入**，LLM 会在任何节点把它当事实。
- 只应在"该条件成立时"由工具/变量更新写入的变量，**默认值应留空**，靠描述说明用途。
- 描述字段约束不了 LLM（描述也进上下文，但 LLM 不把它当硬规则）。

**修复**（用户已验证）：`reason` 默认值清空即可——预约节点上下文里 reason 无值，LLM 无从引用。
> 顺带：原默认值有错别字"逾期**为**还款"（应为"逾期未还款"），若需保留默认值请一并修正。
