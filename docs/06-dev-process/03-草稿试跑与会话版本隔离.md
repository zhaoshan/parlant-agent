# 草稿试跑 与 会话 Agent 版本隔离（设计）

> 2026-09-23 设计稿。需求：**保存草稿即可试跑**（校验未发布变更是否生效），
> **不影响线上正在服务的 Agent**；session 需记录所属 Agent 状态/版本。
> 依据源码事实：`AgentRegistry.load` 按 `definition.agent.id` 建实体；引擎
> `read_agent(session.agent_id)` 处理会话（会话只绑 agent_id，无版本快照）。

---

## 1. 核心矛盾与机制

| Parlant 事实 | 含义 |
|---|---|
| Agent 实体按 `agent.id` 唯一（同 id 只能一个） | 同 id 不能放"草稿版 + 线上版"两个实体 |
| 会话只存 `agent_id`，处理时 `read_agent(agent_id)` 读**当前**实体 | 无"会话级版本快照"；同 id 新版本加载后，该 id 全部会话切新版本 |
| `AgentRegistry.load` 按 id 建实体 | **不同 id（后缀）可并存多个实体**，互不干扰 |

**推论**：要"草稿试跑不影响线上"，必须让**草稿用一个独立的 agent 实例**——
把草稿定义以**后缀 id（`{agent_id}@draft`）**加载进 runtime，试跑会话绑定该后缀 id。
线上 published 实体（裸 id）保持不动，完全隔离。

> **子实体 id 也要隔离（2026-09-23 补）**：定义层实体 id（旅程 `jny_*`、状态 `sta_*`）进的是
> 引擎**全局**存储（不按 agent 隔离）——旅程 id 全局唯一（重复报 `already exists`）、状态 id 重复时
> `insert_one` **静默覆盖**（互相污染）。因此 loader 加载带 `@` 后缀的实例时，旅程/状态 id 统一加
> 实例后缀（如 `jny_LuAwQZ@draft`）；published 主实例无后缀，id 与定义层完全一致（追踪直接对账，
> 草稿实例的日志/轨迹里剥掉 `@...` 后缀即定义层 id）。指南/术语/变量/话术为 SDK 随机 id，本就无冲突。
> （此修复随"loader 显式传旅程 id"引入：之前旅程随机 id 天然不冲突，显式 id 后同定义多实例并存必撞。）

> **热加载旅程必须补评估（2026-09-23，关键）**：分叉推进依赖节点指南上的
> `journey_node.reachable_follow_ups` 元数据（条件表），它由 SDK **评估**阶段
> （`_process_evaluations` → `_apply_single_evaluation`）产出——但该阶段只在 `__aexit__`
> 跑一次，服务于启动前已加载的实体；**publish/rollback 推送、@draft 热加载的实体永远等不到
> 它** → 条件表为空 → 运行期 fork 选择任何回答都是 `invalid condition id` → 旅程无法推进
> （日志 paths 停在 [None]，agent 凭自由指南乱答）。修复：`AgentLoader.load` 装配完即
> `asyncio.create_task` 后台逐旅程 `evaluate_journey`（内容哈希=旅程id+节点id+边id，缓存
> 在 parlant-data/evaluation_cache.json，未变秒回）+ `_apply_single_evaluation` 应用，
> `entity_cq` 监听节点变更投影到指南。**必须后台化**：全量评估是逐节点多次 LLM 调用，
> 实测 ~8 分钟，阻塞会拖死 load 响应/会话创建（server 侧 load 超时已加至 600s）。评估完成
> 前 entry/普通节点可用、fork 暂不可推进；runtime 日志 `✅ 旅程评估完成：… (jny_xxx[@draft])`。

## 2. 目标架构

```
定义层(server, Mongo)：agent_id + 多版本(draft/published/archived)

runtime 实例：
  · 线上 published → agent 实例 id = `{agent_id}`          （现状）
  · 草稿试跑      → agent 实例 id = `{agent_id}@draft`      （新增：按草稿定义后缀加载）

会话台账 user_sessions 新增字段：
  · agent_id           （语义 id，如 onb-094c4bbe2663）
  · agent_instance_id  （实际绑定 runtime 实例，如 onb-094c4bbe2663 或 onb-094c4bbe2663@draft）
  · agent_version      （线上=发布版本号 v1.0.0；草稿="draft"）
  · agent_status       （published / draft）

POST /sessions 绑定 agent_instance_id → Parlant 会话 agent_id = 实例 id
→ 草稿会话行为来自草稿实体，线上会话行为来自线上实体，互不影响
```

## 3. 试跑流程（模拟对话）

1. 模拟对话「新对话」：选 Agent 后，来源选项：
   - **当前草稿（含未发布变更，默认）** → 用 draft 实例
   - **线上版本 vX.X.X** → 用 published 实例
2. 选"当前草稿"时：server 取最新 draft 定义 → 若 `{agent_id}@draft` 尚未加载或定义已变更，
   先 push runtime 加载（复用 `POST /internal/agents/{id}/load`，id=后缀）→
   `POST /api/sessions`（agent_instance_id=后缀 id，source=simulate, agent_status=draft）→ 落台账。
3. 会话处理走 draft 实体 → **校验当前变更是否生效**（改的指南/旅程立刻可测）。
4. 线上 published 实体/会话零影响。

## 4. 发布流程（对线上的影响策略）

- **Parlant 原生**：发布 = 热加载新版本覆盖 `{agent_id}` 实体 → **线上所有该 agent 会话后续消息用新版本**
  （进行中会话无快照，直接切换）。
- **是否接受？→ 待用户确认（§确认 2）**：
  - **A. 接受原生**（阶段3 采用）：线上会话一般短，发布即切换可接受。
  - **B. 阶段5 增强「发布不中断进行中会话」**：published 也用**版本实例**（`{agent_id}@v1.0.0`），
    会话创建时快照绑定当时版本实例；发布 v1.1.0=加载新实例，v1.0.0 实例保留服务旧会话，
    旧会话自然结束后再卸载旧实例（需版本实例生命周期管理）。

## 5. 校验"变更是否生效"的体现

- 台账 session 带 `agent_version/agent_status` → 观测/列表可区分"草稿会话"与"线上会话"。
- 试跑草稿会话的行为（旅程命中、工具调用、回复内容）即为草稿定义的行为 → 可对比线上会话。

## 6. draft 实例生命周期（待确认）

- 方案 A：试跑会话关闭后**立即卸载** `{agent_id}@draft`（省资源，下次试跑重载，草稿变更自动生效）。
- 方案 B：**缓存保留**直到草稿再变更或 agent 卸载（试跑更快，但占 embedding 缓存/内存）。

## 7. 实施范围

- server：`POST /api/internal/...` 或复用 load 端点按后缀加载；`user_sessions` 加
  `agent_instance_id/agent_version/agent_status` 字段（迁移）；`POST /api/sessions` body 支持
  `agent_instance_id + agent_version + agent_status`；试跑草稿=server 取 draft 定义 → 后缀 id 加载。
- runtime：load 端点已按 definition.agent.id 建实体，后缀 id 天然支持；`_load_published_agents`
  只加载 published（现状不变）。
- web：模拟对话「新对话」加来源选择（当前草稿 / 线上版本）；列表/观测显示会话所属版本/状态。
