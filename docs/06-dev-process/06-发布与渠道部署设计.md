# 发布与渠道部署设计（deploy：版本 × 渠道）

> 2026-09-24 增补。背景：原"发布/回滚"演进出 **deploy（版本 × 渠道部署矩阵）** 能力——不同渠道可部署不同 Agent 版本；同渠道内切换部署版本即**快速回滚**（无需 rollback 覆盖语义，版本永远向前保留在历史）。本设计为**阶段5**（plan 阶段5 任务 5.8）的前置设计，当前仅记录架构与接入形态。
>
> 关联：`docs/06-dev-process/03-草稿试跑与会话版本隔离.md`（`@draft` 后缀实例隔离，机制复用）、`docs/06-dev-process/02-客户信息与Variables覆盖机制.md`、plan 阶段4 4.5（版本向前）、plan 阶段5 5.8。

## 一、问题与决策

- **现状**：发布 = server 自动递增版本 → 推 runtime 热加载覆盖**同一个 published 实体** → 线上进行中会话切到新版本（无会话级版本快照，阶段3 接受）。
- **演进**：deploy 把"发布"拆成两步——**发布（产生新版本，版本向前）** 与 **部署（版本 × 渠道 映射）**。
- **快速回滚**：渠道内把部署版本从 v3 切回 v2 = 该渠道**新会话**立即走 v2；不做"回滚覆盖"（v3 不删，历史保留）。
- **简化决策**：Agent 编辑页只做「版本历史 + 差异对比」（阶段4 已落地）；deploy 属阶段5，不在编辑页做。

## 二、核心机制

### 2.1 部署表（server 定义层）

MongoDB 新增 `agent_deployments` 集合（server 独占写，与 `agent_definitions` 同属定义层）：

```text
{ agent_id, channel, version, updated_at, updated_by }
唯一索引：(agent_id, channel)
```

- `channel` 与 `user_sessions.source` 对齐：`online / simulate / auto_sim / dingtalk / feishu / web_widget`（阶段5 扩展后三者）。
- 发布流程追加：`publish` 成功后默认写入部署表（全渠道 → 目标版本，或指定渠道）。
- 会话创建：`POST /api/sessions` 的 `source`/渠道参数 → server 查 `agent_deployments` 解析应绑定的**版本实例**；无部署记录回退 `published` 最新。

### 2.2 版本实例化（复用 @draft 后缀机制）

- 版本实例 id：`{agent_id}@{version}`（如 `onb-xxx@1.2.0`），与 `{agent_id}@draft` 同一套 `AgentLoader._instance_suffix` 隔离机制——定义层实体 id（`jny_*`/`sta_*`）加实例后缀，避免全局存储冲突。
- 会话绑定实例：`user_sessions.agent_instance_id = {agent_id}@{version}`（现已有该列）。
- **进行中会话保持原实例**：会话创建时已绑定实例，引擎按 `session.agent_id` 读实体 → 实例即会话级版本快照（解决阶段3 "进行中会话切新版本" 的遗留）。
- runtime 需按需加载版本实例：server 在会话创建时若实例未加载 → 取该版本定义 `POST /internal/agents/{id}@{version}/load`（幂等，已有能力）；闲置实例可按 LRU 卸载（对齐 `@draft` 的立即卸载策略，可放宽为定时）。

### 2.3 发布 / 部署 / 回滚语义

| 操作 | 行为 |
|---|---|
| 保存草稿 | 不变：`agent_definitions` draft 槽 |
| **发布** | 草稿 → 新版本号（patch+1）→ 落 `agent_definitions`（published，旧 published 置 archived）→ 默认部署到全部渠道 |
| **部署**（新） | `PUT /api/agents/{id}/deploy` body `{channel, version}` → 写部署表 → 该渠道新会话走 `{id}@{version}` |
| **快速回滚**（=部署旧版本） | 渠道部署版本改指旧版本；进行中会话不受影响 |
| rollback（旧端点） | 保留（server 已实现），语义弱化为"整站切回旧版本 = 全渠道部署旧版本"；UI 弱化 |

## 三、渠道接入形态（初步）

统一经 **server 会话代理 + SSE 透传**，web 不直连 runtime：

- **web widget**：web 聊天组件嵌入式形态——第三方站点挂 `<script>` 注入 iframe/widget，固定 `channel=web_widget`；复用现有 `/api/sessions` + SSE 事件流。
- **钉钉机器人**：钉钉开放平台机器人 webhook（收消息）/ 事件订阅（群聊 @）→ server 新增渠道适配层，把消息转为 `POST /api/sessions/{id}/events`，Agent 回复经回调/流式转回钉钉。
- **飞书机器人**：飞书事件订阅 + 机器人发送消息 API，机制同钉钉（不同 SDK 适配）。
- 渠道适配层形态：server 独立 router（`/api/channels/{channel}/*`）或独立小服务，统一调 SessionService。

## 四、影响面

- **台账**：`user_sessions.source` 即渠道；观测/仿真按渠道筛选天然可用。
- **变量覆盖**：客户维度覆盖不受渠道影响（key=customer.id 全局），多渠道同客户共享。
- **消息历史/SSE**：widget/机器人不一定要 SSE 前端流式；渠道适配层可选择 block（一次性完整回复）或流式推送。
- **鉴权/限流**：渠道入口在 server 侧统一加鉴权（钉钉/飞书签名校验、widget 站点白名单）。

## 五、落地顺序（阶段5 内）

1. 部署表 + `publish` 默认部署 + `deploy` 端点 + 会话按渠道解析版本实例
2. 版本实例化 `{agent_id}@{version}`（复用 3.12 机制）+ 会话绑定/卸载
3. web widget（复用现有 web 组件，改动最小）
4. 钉钉机器人 → 飞书机器人（渠道适配层）
