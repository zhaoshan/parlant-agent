## 任务清单

### 5.1 用户输入审核（Input Moderation）
- 集成 Lakera Guard 或 Llama Guard（见 `docs/03-production/02-用户输入审核.md`）。
- 在 `create_event` 链路（moderation 参数）启用分级：`moderate` / `paranoid`。
- 命中违规时返回预设拒绝话术并可告警。

### 5.2 人工转交（Human Handoff）
- 工具/指南触发把 session `mode` 改为 `manual`，引擎停止自动回复（见 `docs/04-execution-chain/01-业务执行链路总览.md` 阶段①）。
- web 增加"人工坐席"工作台：查看待接管会话、代 AI 回复（`HUMAN_AGENT_ON_BEHALF_OF_AI_AGENT`）、恢复自动（return-to-AI）。

### 5.3 API 加固（API Hardening）
- **parlant-agent-server（对外入口）**：JWT 认证、细粒度 operation 授权（见 `docs/03-production/04-API增强.md`）；CORS 收紧到指定域名；按 IP 限流（`limits`）。
- **parlant-agent-runtime**：Parlant REST/SSE 仅绑内网；`/internal/*` 加内网鉴权（shared token/mTLS），不暴露公网。

### 5.4 可观测看板
- langfuse 已能看单 trace；此步做**聚合**：指南命中率、工具调用分布与成功率、`message_generation_duration`/`match_duration` 趋势、转人工率。
- 关键 trace 属性（`agent_id`/`session_id`）作为过滤维度（在 server/runtime 用 hooks/middleware 注入）。

### 5.5 治理能力（补充能力）
- **审计日志**：配置变更（谁/何时/改了哪个组件）落库可查（server 侧，定义层独占写故天然具备写入点）。
- **版本管理强化**：草稿→评审→发布→回滚流程；变更 diff 报告。
- **对话仿真回归**：预置用例集，发布前经 server 自动跑、比对预期分支；失败阻断发布。
- **Customer 管理**：客户实体/标签/变量维护页（支撑 web 聊天传参）。
- **工具/检索器连接管理**：集中配置 OpenAPI/MCP 工具与向量库连接，含连通性测试按钮。

### 5.6 部署与测试
- **docker compose**：`runtime + server + web + mongo + qdrant + langfuse` 一键起。
- **测试**：runtime 单元/集成测试（loader 幂等性、registry 热更新）；server 代理/发布编排测试；web 组件测试；关键旅程的 e2e 用例。
- **CI**：lint + test + 镜像构建。

### 5.7 runtime 生产化（多实例与高可用）
> 背景：runtime 是有状态执行引擎（会话/journey 路径/变量缓存在内存与本地文档库），单 pod 无法 horizontally scale。本节把它改造为多 pod 可用形态。

- **会话状态外置**：Parlant 文档存储（Agent/Session/Customer/Event/Variable）从本地文件切到共享 MongoDB（2.6 已打底，此处补全 Session/Event 等全部实体）； transient 向量缓存可重建。目标：任一 pod 都能接管任一会话。
- **多 pod 部署**：runtime 无本地状态后可水平扩展；前排负载均衡（round-robin/最少连接）。
- **Agent 实例高可用**：agent 定义发布经 server 推送到**所有** runtime pod（fan-out），各 pod 独立热加载；`/internal/health` 上报加载状态，server 维护 pod 注册表与版本一致性巡检。
- **用户问答故障转移**：SSE 长连接断开时 web 经 server 重连，server 依据健康检查把会话路由到健康 pod；在途事件以 `offset` 续传保证不丢不重。
- **server ↔ runtime 消息队列**：引入 Redis/RabbitMQ——发布事件广播（替代 HTTP fan-out）、问答流量削峰、pod 宕机时的请求重排队；HTTP+SSE 透传保留为同步路径。

## 验收标准

- [ ] 违规输入被拦截并返回预设话术
- [ ] 触发转交后引擎停止自动回复，人工可接管与恢复
- [ ] server 管理 API 未认证不可访问；CORS/限流生效；runtime `/internal/*` 公网不可达
- [ ] 看板能看到各 Agent 的命中/耗时/转人工趋势
- [ ] `docker compose up` 一键起全套并跑通用例
- [ ] **5.7**：≥2 个 runtime pod 同时服务；发布一次定义所有 pod 生效；kill 一个 pod 后，在途问答经 server 重连到健康 pod 且不丢消息

## 风险与提示

- **人工转交状态机**：接管/恢复要处理好在途消息与 offset，避免消息丢失或重复。
- **审核延迟**：paranoid 模式会增加首 token 延迟，权衡体验与安全等级。
- **回归用例维护**：业务旅程变化快，仿真用例需随版本一起维护。
- **会话状态外置的 eventually-consistent 窗口**：MongoDB 切换后，pod 间会话可见性有短暂延迟；故障转移瞬间需容忍重复事件（客户端按 offset 去重）。
- **消息队列引入复杂度**：5.7 队列与现有同步路径并存期间，注意发布/消费语义一致（至少一次 + 幂等消费）。

## 技术债：观测插桩"去 hack 化"改造（后续实施项）

> 现状：为排查旅程/LLM 问题，我们在**可编辑安装的 parlant 源码**里加了 3 处观测插桩
> （`generation.py` 的 `gen_ai.chat` span、`engine.py` 的旅程推进日志 + process 输入输出、
> `journey_next_step_selection.py` 的命中转移条件日志）。直接改源码会让 parlant 升级被覆盖、diff 混乱、不可维护。

**改造项**（详见 `docs/03-production/12-观测插桩去hack化改造.md`）：

- **LLM 输入输出**：改用 litellm 原生 **OTel 回调**（`gen_ai.*` semconv）→ langfuse generation，零 parlant 改动；唯一不确定点是它与 parlant 全局 TracerProvider 的协同，需小实验验证。
- **旅程推进日志**：改用 **EngineHooks** `on_preparation_iteration_end`（官方机制，升级安全）。
- **命中转移条件日志 + process span 输入输出**：判定为冗余，直接弃用（journey_paths 已能定位节点，gen_ai 已给各阶段 LLM I/O）。
- 落地后 `git checkout` 还原 3 处插桩文件，parlant 源码仅剩 2 处**必需** hack（`litellm_service.py` torch 兼容、`opentelemetry.py` 导出开关/噪声采样）。

**验收**：langfuse 每个 trace 的 guideline_matcher / message_generation / tool_caller 下出现 `gen_ai.chat` generation；旅程推进日志经 `configure_hooks` 输出且行为与现插桩一致；parlant 源码无插桩残留。
